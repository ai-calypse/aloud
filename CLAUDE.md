# Aloud

Cross-platform (macOS + Windows) voice dictation. Hold a key, speak, and clean
text lands in whatever app has focus.

Rust does the work, React draws the pixels, Tauri v2 glues them together.
This is a port of a macOS-only Swift app, which stays the reference
implementation until parity — see `PROGRESS.md` for what has landed.

## Layout

```
apps/desktop/          Tauri app
  src-tauri/src/       thin orchestration only — logic belongs in a crate
  src/                 React + TypeScript
  src/lib/bindings.ts  GENERATED by tauri-specta. Never hand-edit.
crates/
  agent/               the command brain: tool loop, Composio, evals
  audio/               mic capture (cpal), resampling, pause segmenter
  engine/              runs the browser task engine (engine/, Node)
  hotkey/              global hotkeys: CGEventTap / WH_KEYBOARD_LL
  llm/                 OpenAI-compatible chat, prompts, rate limits
  meeting/             meeting transcript assembly, note composition
  native/              Mac app actions (AppleScript/JXA) + the no-model fast path
  notes/               markdown notes + search, app data paths
  paste/               clipboard snapshot/restore, synthetic paste
  screen/              screen control through Cua Driver: read, click, type
  selection/           reading the focused app and its selected text
  store/               settings, history, stats, migrations, timings
  transcribe/          local whisper.cpp + cloud whisper + Deepgram streaming
engine/                browser tasks in the user's browser (TypeScript + axd)
evals/                 the evals dashboard: eval runs beside real-use traces
```

## Commands

```sh
pnpm install                # once
pnpm dev                    # run the app
pnpm build                  # bundle (.dmg / .app / .nsis)
cargo test --workspace      # all Rust tests
cargo clippy --workspace --all-targets   # must be warning-free
cargo fmt --all
pnpm --filter @aloud/desktop typecheck
```

Rust lives in `~/.cargo/bin` — `export PATH="$HOME/.cargo/bin:$PATH"` if
`cargo` is not found. Building `transcribe` needs `cmake` (whisper.cpp).

## Skills — load the one for the layer you are touching

This app is four technologies in one repo, and each has a skill carrying
conventions that a general answer will not have. **Load the relevant skill
before writing or reviewing code in that layer**, not after — the point is to
write it right the first time, and half of what these carry is failure modes
that compile fine and break at runtime.

| Touching | Skill |
|---|---|
| `src-tauri/`, `tauri.conf.json`, capabilities JSON, `#[tauri::command]`, `invoke()`, `@tauri-apps/*`, `cargo tauri …` | `tauri-wisdom` |
| Anything in `crates/`, or Rust anywhere | `rust-skills` |
| `apps/desktop/src/**` — components, hooks, state | `vercel:react-best-practices` |
| Any animation, transition or gesture response — anything that opens, closes, resizes, or changes while on screen | `aloud-motion` |
| Reading the Swift reference app for parity | `swiftui-pro` |

Most work here spans two — a new dictation feature is a Tauri command
(`tauri-wisdom`) wrapping crate logic (`rust-skills`) surfaced in React
(`vercel:react-best-practices`). Load both ends, not just the one you started in.

The skill is a floor, not a ceiling. Where it disagrees with a rule written
down in this file, **this file wins** — it was tuned on this codebase, and the
`ponytail:` corner-cuts and porting decisions here are deliberate. Say when you
are overriding a skill and why.

Names are exact. There is no bare `react-best-practices`; the Vercel plugin
prefix is required or the invocation silently does nothing.

## How this codebase is organised

**Logic goes in a crate, not in `src-tauri`.** Crates have no Tauri
dependency, so they are testable with `cargo test` and runnable from an
`examples/` binary without launching the app. `src-tauri` should only wire
crates to commands and events. The Swift app's 4,000-line `AppState` god
object is exactly what this structure exists to avoid.

**The frontend never guesses at Rust's types.** `tauri-specta` regenerates
`src/lib/bindings.ts` on every debug run. Add a `#[tauri::command]`, run the
app, and the typed binding appears.

**Platform differences live in the crate that owns them**, behind `#[cfg]`,
never leaking into app code. `hotkey` is the model: one pure reducer, two
thin OS backends.

## Command mode

Three modes: **Dictation** (hold to talk, text pasted), **Command** (the
Command key, the old Ask key, "hey flow" while dictating, and always-listening
all run one agent) and **Meeting**. A command goes:

1. **Fast path, no model** — `aloud_native::fast`: open/quit installed apps,
   play/pause/next, volume, and obvious web commands ("go to youtube", "search
   lofi on youtube") straight to the browser engine.
2. **The brain** — one tool-calling model at a time, best first
   (`aloud_agent::brains`): Groq `openai/gpt-oss-120b`, then Gemini
   Flash-Lite, then NVIDIA's `nemotron-3.5-lightning` (fast, but it wanders
   over a long run). The ~9,000-token prompt is past Groq's free 8,000 a
   minute, so on a free key Gemini does most of the work. A 429, a 5xx, a dead key or an unreachable endpoint moves the
   command to the next brain mid-run; a tool turn times out at 12s, and a brain
   still cooling down is skipped without a request. Tools, in the order the
   prompt gives them: `ALOUD_*` Mac intent tools (the model writes content into
   their arguments), the connected services the command is about (Composio;
   others load on demand via `ALOUD_MORE_TOOLS`), `ALOUD_BROWSER_TASK`, screen
   control for a Mac app nothing else covers, else an answer.
3. A run of Mac writes that all worked ends on the tool's own confirmation —
   no second model call. A command naming several actions ("take 5 photos",
   "… then …") never ends early; repeatable tools take `times`.

Mac intent tools act in the background without bringing their app forward.
The app, document and project the user was in are merged into a native tool's
arguments after the gate, so neither the model nor the card sees them.

**The gate.** Every write goes through `permissions::gate`, which keys it by app
and action (`slack:send-and-share`), then `agent::permit` reads `grants.json`:

- **Always** runs with no card; **Never** refuses, and the row says "Blocked in
  Settings"; **Ask** shows the approval card. Settings → Permissions edits them.
- **Strict** — paying, permanent deletes, public posting, sharing passwords or
  codes — always asks, never offers Always allow, and ignores Enter.
- **The named-app rule** is the silent defence against injected instructions.
  Once outside content is in the run (the selection, or any read, browser or
  screen result), a write to an app the user never named asks even when it is
  always allowed. The front app counts as named.
- **The card** comes from `preview::render`: a `hand.json` mapping, else a
  generated one (`action-previews.json`), else the schema. `enrich` then names
  ids with reads cut off at 1.5s. The user's exact words to a resolved contact
  or channel count down 3s with Undo instead of waiting for a click.
- **Answers** are revisioned, and whichever comes first wins: a click, a spoken
  reply ("send it", "cancel", "make it …"), the countdown, or the gate being
  cleared. A spoken reply is tried before speech claims a new run, so a card can
  be answered by voice without cancelling its run. Each decision and write is
  logged to `audit.jsonl` (tool, app, decision, never content).

A round's calls are admitted one at a time (gates and questions in order, one
prompt on screen), then run together, three at most, and are reported in call
order. Anything that brings an app forward or types into the front one holds
the process-wide UI lock (`tool_loop::UI`); a native tool that does must be
listed in `aloud_native::takes_front`, or it races its siblings for the screen.

Script user text into apps with `script::run_jxa` (one JSON argument, never
interpolated). Routing changes are checked against the eval, not by feel:

```sh
cargo run -p aloud-agent --example command_eval            # first turn, every brain with a key
cargo run -p aloud-agent --example command_eval -- runs nvidia  # whole runs, tools mocked
cargo run -p aloud-native --example demo -- fast "<said>"  # what the fast path does
pnpm evals                                                 # the dashboard, 127.0.0.1:8091
```

Each eval run is saved to `<app-data>/evals/`, shared by every worktree, so
the dashboard lines a branch's run up against the brain's previous one. It
reads real use from the same folder (`timings.sqlite`, `history.sqlite`,
`engine/log.jsonl`) and shows it apart from the eval, never blended. A
command's words are deliberately not in the timings DB, so a real command
shows its route, tools and rounds but not what was said.

Screen control is the last tier, on trycua's Cua Driver (`crates/screen`, which
shells out to `cua-driver call`): read an app's accessibility tree as numbered
elements, click or type by number, and each action returns the window afterwards.
One yes covers a run, and the first screen call raises the round budget from 5
to 30. Two traps: element numbers belong to a driver *session*, so every call
carries one label (a bare `call` is a session of its own and every click comes
back stale), and an ended label is dead for good, so each run gets a fresh one.
A driver action takes ~1.5–2s — its own post-action window watch, no knob.

## Frontend architecture

```
src/styles/          the design system — every colour, size and curve
  tokens.css         THE palette. A colour not here should not exist
  base.css           document reset + cursor rules, shared by all windows
  motion.css         durations, easings, named animations, reduced-motion
  panel.css          ask/agent window chrome
  overlay.css        the recording overlay — glass pill, drop-down pill, wings
src/components/ui/   shared primitives. Nothing app-specific lives here
src/features/<area>/ one folder per area of the app
src/lib/             logic worth testing away from React
```

**Colours go in `tokens.css`, never in a component.** Tokens come in two
tiers: raw macOS system colours (`--sys-blue`), then semantic names that say
what a colour is *for* (`--card-solid`, `--sep`, `--danger`). Components use
only the semantic tier, through the Tailwind utilities wired up in
`index.css` — `bg-surface`, `text-ink-2`, `rounded-card`. An arbitrary value
like `bg-[var(--card-solid)]` in a component means a token is missing a
utility.

**All four windows load the same palette.** Floating windows (overlay, ask,
agent) declare `data-surface="floating"` on `<html>`, which scopes the
always-dark overrides. It is declared in the markup rather than set from
React so the palette is right on the first paint.

**`cn()` must know about custom tokens.** `lib/utils.ts` extends
tailwind-merge with our class groups. Without it, tailwind-merge sees
`text-ui` (a size) and `text-brand` (a colour) as the same group and silently
drops one — it typechecks, lints, builds, and renders the wrong colour. Add a
token to `@theme inline`, add it to that list.

**Motion is CSS; JavaScript only sets a target or restarts a keyframe.** The
compositor then owns every frame, so animation does not stutter while React
renders. Durations and curves come from `motion.css` — a component inventing
its own `240ms cubic-bezier(...)` will drift out of step with everything
around it. Reduced motion is one global switch that collapses durations to
1ms rather than setting `animation: none`, which can strand an element on its
opening frame.

The one exception is motion whose target can change while it is still moving —
a status that swaps three times a dictation, a drag, anything retargeted
mid-flight. `motion.css`'s springs are baked into `linear()`, and a baked curve
redirected halfway restarts from zero velocity; `lib/spring.ts` integrates a
real one per frame and carries its momentum through. Choosing between the two
is the first decision in any animation here — `aloud-motion` covers it, along
with the failure modes that render fine and still feel wrong.

**Before adding markup, check `components/ui/`.** The search field, the
grouped card, the hairline row, the pane title and every button shape already
exist. Each of them was extracted after being copy-pasted into two or three
files and drifting apart.

## Conventions

- **Comments say why, not what.** A comment earns its place by explaining a
  constraint the code cannot: why `FastFixedIn` and not the FFT resampler,
  why a daily rate-limit outranks `retry-after`. Never narrate the next line.
- **Mark deliberate corner-cuts** with a `ponytail:` comment naming the
  ceiling and the upgrade path, e.g. `// ponytail: linear scan — SQLite FTS
  is the upgrade path if it gets slow`.
- **Test the logic that can silently be wrong**, not the getters. Every bug
  found so far (empty WAVs, one-shot hotkeys re-firing) got a regression test
  named for the failure.
- **Port intent, not syntax.** Where Swift logic was tuned on real data —
  the hallucination thresholds, the rate-limit header precedence — port it
  verbatim and say so. Where it was working around AppKit, use the better
  Rust tool.
- Keep it minimal. If two lines do it, do not write ten.

## Non-obvious things that will bite you

- **whisper.cpp prints to stdout from C.** Without
  `whisper_rs::install_logging_hooks()`, model load takes 19s instead of
  200ms and the log fills with junk.
- **`ProjectDirs::data_dir()` is wrong for this app.** It yields
  `app.Aloud.Aloud` on macOS; the Swift app uses a plain `Aloud` folder and
  migration reads from it. Use `aloud_notes::data_dir()`.
- **Tauri's `global-shortcut` plugin is unusable here.** No modifier-only
  bindings, no hold-vs-tap, cannot swallow events. Hence `crates/hotkey`.
- **TIS/TSM keyboard-layout APIs abort the process off the main thread** on
  modern macOS (`dispatch_assert_queue` → SIGTRAP), and enigo's
  `Key::Unicode` lookup calls them. Every synthetic key chord must go through
  `aloud_paste`'s `on_main_thread`; calling enigo from a tokio worker or the
  event-tap thread kills the app with no Rust panic message.
- **AppleScript-synthesized keys arrive with keycode 0.** `osascript` cannot
  test the hotkey path; post a real `CGEvent` instead.
- **`specta`/`tauri-specta` are exact-pinned RCs** that move in lockstep. Do
  not loosen to `^`.
- **Bindings are emitted relative to the crate dir**, so `cargo run -p aloud`
  must run from `apps/desktop/src-tauri`. `pnpm dev` handles this.
- **Reading the notch touches AppKit through `objc2`, with two traps.**
  `NSScreen.screens`'s `count` reports an unsigned encoding that objc2's
  debug-only check rejects and *aborts* the process — the `relax-sign-encoding`
  feature on `objc2` (a direct dep) fixes it. And a menu-bar/notch overlay must
  set its `NSWindow` level to `NSScreenSaverWindowLevel`; a floating-level
  window is clamped below the menu bar. `NSScreen` calls must run on the main
  thread — the notch is measured once in `setup`.

## Verifying

Unit tests do not prove OS integration, and this app is almost entirely OS
integration. Anything touching audio, keys, or the clipboard gets an
`examples/` binary that exercises real hardware, and the result goes in the
PR body. Two of the bugs above passed their unit tests before real hardware
disproved them.

## Git

One branch per feature, PR into `main`. PR bodies state what was verified
and, honestly, what was not — every PR so far carries a ⚠️ noting the Windows
path is unexercised.

**CI does not pass, and that is not a signal.** The Actions runners are
unbilled on the free tier, so the workflows fail or never start regardless of
the code. A red PR means nothing here; `mergeStateStatus: UNSTABLE` is the
normal state and merges go ahead through it.

The cost is that nothing is checked for you, so the local run *is* the gate.
Before merging, actually run them:

```sh
cargo clippy --workspace --all-targets   # must be warning-free
cargo test --workspace
pnpm --filter @aloud/desktop typecheck
pnpm --filter @aloud/desktop test
```

Say in the PR body which of these you ran, the same way you say what was
verified on real hardware. "CI is green" is never available as evidence.
